1. VISÃO GERAL
--------------------------------------------------------------------------------

Nome do Projeto : FSSS (Faculdade/Escola — Sistema de Reservas)
Tipo            : Aplicação web institucional (SPA)
Finalidade      : Gerenciamento de reservas de espaços e equipamentos em
                  instituição de ensino. Professores reservam salas, laboratórios,
                  auditórios e equipamentos como projetores e notebooks;
                  administradores gerenciam o sistema por um painel dedicado.

7. AUTENTICAÇÃO (src/contexts/AuthContext.tsx)
--------------------------------------------------------------------------------

Mecanismo
  Sessão armazenada em localStorage com chave "fsss_session"
  Estrutura: { user: User, expiresAt: number }
  TTL: 8 horas (SESSION_TTL_MS = 28.800.000 ms)
  Na inicialização: verifica expiração e remove sessão inválida

API exposta
  user          Objeto User atual (null se não autenticado)
  login(email, password)   Chama fn_login via RPC, popula a sessão
  logout()      Remove a sessão do localStorage

Serviço (src/services/auth.ts)
  signIn(email, password)  Invoca RPC fn_login, retorna dados do usuário ou null

Notas de segurança
  Senha nunca trafega em texto puro (hash bcrypt no banco via pgcrypto)
  Sem Supabase Auth nativo — toda autenticação é via funções RPC com SECURITY DEFINER
  RLS das tabelas usa a role "anon" com políticas específicas por operação

12. BANCO DE DADOS (Supabase / PostgreSQL 15)
--------------------------------------------------------------------------------

12.1 Tabelas
-------------

usuarios
  id            UUID, PK, DEFAULT gen_random_uuid()
  nome          VARCHAR(255), NOT NULL
  email         VARCHAR(255), UNIQUE, NOT NULL
  senha_hash    TEXT (bcrypt via pgcrypto)
  perfil        ENUM(admin | professor), NOT NULL
  ativo         BOOLEAN, DEFAULT TRUE
  criado_em     TIMESTAMPTZ, DEFAULT now()
  atualizado_em TIMESTAMPTZ

itens
  id            UUID, PK
  nome          VARCHAR(255), NOT NULL
  descricao     TEXT
  categoria     ENUM(espacos | instrumentos), NOT NULL
  imagem_url    TEXT
  disponivel    BOOLEAN, DEFAULT TRUE (soft delete)
  total_unidades INTEGER, NULL para espaços, obrigatório para equipamentos
  criado_em     TIMESTAMPTZ
  atualizado_em TIMESTAMPTZ
  Constraint: espaços sem unidades, equipamentos com unidades obrigatórias

horarios
  id            SERIAL, PK
  label         VARCHAR(20), UNIQUE (ex.: "07:00 – 07:50")
  hora_inicio   TIME
  hora_fim      TIME
  is_intervalo  BOOLEAN (marca intervalo/break)
  ordem         SMALLINT (ordem de exibição)

reservas
  id            UUID, PK
  grupo_id      UUID, NULL (agrupa espaço + equipamento)
  usuario_id    UUID, FK → usuarios
  item_id       UUID, FK → itens
  data_reserva  DATE
  quantidade    INTEGER, DEFAULT 1
  status        ENUM(confirmada | cancelada)
  criado_em     TIMESTAMPTZ
  cancelado_em  TIMESTAMPTZ, NULL
  Constraint: cancelado_em deve ser preenchido somente quando status=cancelada

reserva_horarios
  reserva_id    UUID, FK → reservas (ON DELETE CASCADE)
  horario_id    INTEGER, FK → horarios
  PK composta: (reserva_id, horario_id)

dias_bloqueados (opcional)
  id            UUID, PK
  data          DATE, UNIQUE
  motivo        TEXT
  criado_em     TIMESTAMPTZ


12.2 Views
-----------

vw_reservas_detalhadas
  JOIN denormalizado: reservas + usuarios + itens + horarios
  Agrega horários como array: horarios_labels (TEXT[])
  Utilizada para relatórios admin e consultas do frontend


12.3 Funções RPC (SECURITY DEFINER)
-------------------------------------

fn_login(p_email TEXT, p_senha TEXT)
  → TABLE(id, nome, email, perfil)
  Verifica senha bcrypt. Retorna dados do usuário se ativo.

fn_criar_reserva(p_usuario_id, p_item_id, p_data, p_horario_labels[], p_quantidade, p_grupo_id)
  → UUID (id da reserva criada)
  Insere atomicamente em reservas + reserva_horarios.

fn_criar_item(p_admin_id, p_nome, p_descricao, p_categoria, p_imagem_url, p_total_unidades)
  → void
  Cria espaço ou equipamento (com validação de admin).

fn_atualizar_item(p_admin_id, ...)
  → void
  Atualiza item (com validação de admin).

fn_deletar_item(p_admin_id, p_item_id)
  → void
  Soft delete: define disponivel = FALSE.

fn_criar_usuario(p_admin_id, p_nome, p_email, p_senha)
  → UUID
  Faz hash bcrypt da senha e cria professor.

fn_atualizar_usuario(p_admin_id, p_id, p_nome, p_email, p_senha)
  → void
  Atualiza dados do professor.

fn_deletar_usuario(p_admin_id, p_usuario_id)
  → void
  Remove professor.

fn_listar_professores()
  → TABLE(id, nome, email, ativo, criado_em)
  Retorna todos os professores sem expor hashes de senha.


12.4 Políticas RLS
-------------------

Role "anon" (usada pelo cliente frontend)
  itens              SELECT (leitura pública)
  horarios           SELECT (leitura pública)
  vw_reservas_detalhadas  SELECT
  reservas           INSERT, SELECT, UPDATE (colunas específicas para update)

Storage bucket "item-images"
  Leitura pública (GET)
  Upload permitido para role anon (INSERT)

13. FUNCIONALIDADES DO SISTEMA
--------------------------------------------------------------------------------

1. Autenticação customizada
   Bcrypt-based, TTL de 8 horas, persistência em localStorage

2. Controle de acesso por perfil
   Painel admin vs. portal do professor

3. Fluxo de reserva
   Categoria → Item → Data → Slots de horário → Quantidade → Confirmação

4. Reservas atômicas
   RPC garante inserção simultânea de slots e metadados

5. Reservas em grupo
   Espaço + equipamento reservados juntos, canceláveis como unidade

6. Soft delete de itens
   Itens marcados como indisponíveis; histórico preservado

7. Gerenciamento de horários
   Grade fixa 07:00–17:30, períodos de intervalo marcados

8. Datas bloqueadas
   Admin pode bloquear datas específicas (feriados, eventos)

9. Relatórios em PDF
   Resumos diários de reservas exportáveis

10. Upload de imagens
    Imagem por item via Edge Functions

11. Design responsivo
    Layouts desktop / tablet / mobile

12. Disponibilidade em tempo real
    Cache TanStack Query + reload manual

13. Gestão de professores
    Admin cria, edita e remove contas de professores

14. Histórico de reservas
    Usuário acessa reservas futuras, passadas e canceladas com abas

14. DECISÕES ARQUITETURAIS
--------------------------------------------------------------------------------

RPC em vez de PostgREST direto
  Funções SECURITY DEFINER permitem hash de senha seguro e operações
  restritas a admin sem expor lógica via REST puro.

Autenticação customizada
  Bcrypt + RPC mantém a senha hasheada no banco; nenhum texto plano trafega.
  Evita dependência do Supabase Auth nativo.

Soft delete
  Preserva dados históricos para auditoria; itens desativados não aparecem
  na listagem mas continuam nas reservas antigas.

Group IDs em reservas
  Permite cancelar espaço + equipamento em uma única operação, mantendo
  coesão semântica da reserva composta.

Sessão em localStorage
  Simples, funciona offline, sem necessidade de session storage server-side.
  TTL de 8h alinhado ao turno de trabalho.

TanStack React Query
  Gerenciamento automático de cache, re-fetch em background e deduplicação
  de requisições sem Redux ou contextos complexos.

shadcn/ui + Radix UI
  Componentes consistentes e acessíveis sem overhead de bibliotecas monolíticas.

Vite + SWC
  Build e hot-reload extremamente rápidos para desenvolvimento.

16. COMO EXECUTAR O PROJETO
--------------------------------------------------------------------------------

Pré-requisitos
  Node.js >= 18
  Conta no Supabase (ou Supabase local via CLI)

1. Clonar o repositório
     git clone <url-do-repo>
     cd projeto-fsss

2. Instalar dependências
     npm install

3. Configurar variáveis de ambiente
     cp .env.example .env
     # Preencher VITE_SUPABASE_URL e VITE_SUPABASE_ANON_KEY

4. Configurar o banco de dados (na interface do Supabase ou via psql)
     Execute em ordem:
       database/schema.sql
       database/functions.sql
       database/seed.sql
       database/fixes.sql
       database/final_auth_fixes.sql
       database/storage_policies.sql
       database/storage-rls-policies.sql
       database/file_upload_fix.sql

5. Iniciar servidor de desenvolvimento
     npm run dev
     Acesse http://localhost:8080

6. Build de produção
     npm run build
     # Saída em dist/

7. Executar testes
     npm test          # Vitest (unitários)
     npx playwright test  # E2E (requer servidor rodando)
